# 📘 공통 소스코드 작성·표시·주석 표준 v1.0

**적용 대상:** C, Verilog/SystemVerilog, Python, HTML, CSS, JavaScript, Shell 및 기타 교육·개발 소스코드  
**적용 문서:** [범용 웹페이지 제작 표준](../web/YJWS_v1.0.md) · [플로우차트 작성 표준](flowchart-rules.md) · [MBV SoC 전용 규칙](../fpga-soc/MBV_SOC_rules.md)  
**핵심 원칙:** 실행 정확성 → 원본 보존 → 일관된 들여쓰기 → 읽기 쉬운 주석 → 코드·해설·도식 일치

## 1. 원본 보존과 수정 범위

1. 실제 프로젝트에서 검증된 원본 소스는 **서식 개선을 이유로 임의 변경하지 않는다.**
2. 원본 코드의 표기와 이 문서의 권장 서식이 다르면 원본을 우선 보존한다. 필요하면 별도 **교육용 서식 정리본**을 제공하고 원본과 구분한다.
3. 주석만 추가해도 변경된 파일이므로, 원본과 구분하고 실제 빌드·시뮬레이션·보드 검증 여부를 다시 명시한다.
4. 단순 들여쓰기·공백·주석 정리와 기능 수정은 반드시 구분한다.
5. **기능 변경이 필요한 경우** 변경 이유·위치·검증 결과를 기록한다.
6. 기능이 동일한 표현 변경은 ‘대체 표현’이라고 부르고, 실제 결함을 수정한 경우에만 ‘해결 코드’라고 한다.

## 2. 언어별 들여쓰기

| 언어 | 기본 들여쓰기 | 추가 원칙 |
|---|---|---|
| C | 공백 4칸 | 함수·조건·반복 블록을 한 단계씩 들여쓰기 |
| Verilog / SystemVerilog | 공백 4칸 | `module`, `always`, `begin/end`, `case/endcase` 계층 정렬 |
| Python | 공백 4칸 | 탭과 공백 혼용 금지, 블록은 콜론 뒤 들여쓰기 |
| HTML | 공백 2칸 | 요소 중첩 단계에 따라 들여쓰기 |
| CSS | 공백 2칸 | 선언을 줄별로 배치, 닫는 중괄호 정렬 |
| JavaScript | 공백 2칸 | 블록별 중첩, 세미콜론 정책 일관성 |
| Bash/Shell | 공백 2칸 권장 | `if/fi`, `for/done`, 함수 블록 정렬 |
| 기타 언어 | 해당 언어의 공식 관례 | 프로젝트에 이미 합의된 서식이 있으면 그 기준 우선 |

- 들여쓰기는 **탭 대신 공백**을 기본으로 한다. 기존 프로젝트에서 탭을 명시적으로 사용한다면 혼용하지 않고 원본 관례를 따른다.
- 빈 줄은 함수·논리 단계 구분에 사용하고, 불필요한 연속 빈 줄은 제거한다.
- 블록 내부의 연산자·쉼표 뒤 공백은 언어 문법과 프로젝트 관례에 맞춘다.
- 연산 우선순위가 헷갈리는 조건식에는 괄호를 사용하되, 기존 코드의 동작을 바꾸지 않는다.
- 지나치게 긴 한 줄은 읽기 쉬운 지점에서 나눈다. **짧은 함수 호출은 1줄, 긴 인자는 가능하면 2줄**로 정리한다. 문법·가독성 때문에 필요하면 예외를 허용한다.
- 권장 줄 길이는 약 **100~110자 이내**이지만, 실제 코드·언어별 도구의 기준이 더 중요하다.

## 3. 중괄호·블록·조건문 정렬

- 같은 파일에서 중괄호 스타일을 통일한다. 새 예제는 C·JavaScript에서 `if (...) {` 형식을 기본으로 한다.
- `else`는 해당 `if`의 닫는 중괄호와 같은 들여쓰기 단계에 둔다.
- Verilog의 `begin`과 `end`, `case`와 `endcase`는 논리 블록의 시작과 끝을 명확하게 정렬한다.
- 조건문·반복문이 중첩되면 한 단계씩 들여쓰고, 과도한 중첩은 기능 단위 분리를 검토한다.
- 단일 문장 분기라도 교육용 예제에서는 중괄호를 사용해 범위를 명확하게 하는 편을 권장한다. 단, 검증된 원본 코드는 임의로 고치지 않는다.

## 4. 주석의 목적·위치·언어

- 주석은 **무엇을 하는가**뿐 아니라 **왜 필요한가**, **어떤 조건에서 동작하는가**를 짧고 정확한 **한글**로 설명한다.
- 함수·모듈 시작 부분에는 역할과 중요한 입출력을 설명한다.
- 상태 전이·비트 마스크·레지스터 접근·타이밍·예외 처리 등 초보자가 오해하기 쉬운 부분에는 코드 **바로 위**에 주석을 둔다.
- 변수명·연산자만 그대로 읽는 불필요한 주석은 넣지 않는다.
- 같은 내용을 코드 주석과 본문 해설에서 장황하게 반복하지 않는다. 코드 주석은 핵심, 본문은 원인·과정·결과를 설명한다.
- 설명용 주석이 실제 동작과 어긋나면 **코드를 먼저 확인하고 주석을 정정**한다.
- 코드의 의미를 바꾸는 주석 처리(기존 실행문 비활성화)는 **기능 변경**이므로 무단 수행하지 않는다.

### 4.1 언어별 주석 문법

| 언어 | 일반 주석 | 여러 줄 주석 |
|---|---|---|
| C / Verilog / JavaScript | `// 설명` | `/* 설명 */` |
| Python / Shell | `# 설명` | 여러 줄의 `#` 사용 |
| HTML | `<!-- 설명 -->` | 동일 |
| CSS | `/* 설명 */` | 동일 |

- JSON(제이슨, 데이터 교환 형식) 표준 문서에는 주석 문법이 없으므로 JSON 코드 내부에 주석을 넣지 않는다.
- Python의 삼중 따옴표는 문서 문자열로 사용하며, 단순 주석을 위해 남용하지 않는다.

## 5. 변경 사항 표시

기존 코드의 추가·변경 위치에는 해당 코드 **바로 위에** 다음과 같이 표시한다.

```c
// (추가) UART 명령 문자열의 종료 여부를 확인한다.
if (line_complete) {
    process_command();
}
```

- `// (추가) 역할 또는 이유`
- `// (변경) 기존 동작과 변경 이유`
- `// (삭제) 삭제 대상과 이유`는 **변경 이력·차이 비교 자료**에서 사용한다. 삭제된 코드를 실행 소스에 억지로 남기지 않는다.
- Python은 같은 의미로 `# (추가)`, `# (변경)` 등을 사용한다.
- 주석을 코드에 삽입하면 문법·실행에 영향이 없는지 다시 확인한다.

## 6. C 코드 작성 기준

- 함수의 역할·입력 인자·반환값·오류 처리를 필요에 따라 설명한다.
- 포인터·형변환·비트 마스크·메모리 매핑 입출력은 실제 자료형과 주소를 확인한 뒤 주석을 작성한다.
- `u8`, `u32`, `Xil_In32`, `Xil_Out32` 등 전용 자료형·API는 **표준 C 언어 자체의 키워드가 아님**을 설명하고 실제 헤더·플랫폼 정의를 확인한다.
- 문자열 명령과 종료 문자를 원본과 정확하게 일치시킨다.
- 매크로·상수의 의미를 추정으로 확정하지 않는다.

## 7. Verilog / SystemVerilog 코드 작성 기준

- 포트 방향·폭, 클록·리셋 극성, 순차/조합 블록, 상태명, 핸드셰이크 조건을 실제 코드에 맞춰 설명한다.
- `<=`(비차단 대입)과 `=`(차단 대입)의 의미를 혼동하지 않는다.
- 축약된 비트 연결·시프트 레지스터·슬라이스에는 비트별 동작을 주석으로 풀어쓴다.
- `begin/end`, `case/endcase`의 들여쓰기를 통일한다.
- 원본에 없는 `default`·리셋·상태를 설명 편의를 위해 임의로 추가하지 않는다.
- 합성 대상 코드와 테스트벤치 코드를 구분한다.

```verilog
// 예시: 3비트 시프트 레지스터의 비트 이동
// shift_reg[2] <= shift_reg[1];
// shift_reg[1] <= shift_reg[0];
// shift_reg[0] <= serial_in;
always @(posedge clk) begin
    shift_reg <= {shift_reg[1:0], serial_in};
end
```

## 8. Python 코드 작성 기준

- PEP 8(펩 에이트, 파이썬 코드 스타일 지침)을 기본 참고로 하되 기존 프로젝트의 검증된 서식을 보존한다.
- 함수·조건·반복은 공백 4칸 들여쓰기를 적용한다.
- 함수·클래스·변수 이름은 역할을 알 수 있도록 작성한다.
- 실행 예제의 코드와 예상 출력은 분리한다.
- 짧은 예제는 **코드 → 실행 결과** 순서로 제시하고, 필요한 해설은 묶음 뒤에 간결하게 작성한다.

## 9. HTML / CSS / JavaScript 작성 기준

- HTML은 요소별 계층을 들여쓰고 의미 있는 구조 태그를 사용한다.
- CSS는 선택자·선언·닫는 중괄호를 읽기 쉽게 줄별로 배치한다.
- JavaScript는 함수·이벤트·조건·오류 처리를 들여쓰기한다.
- 공개용 압축 파일을 별도로 생성할 수 있지만, **유지보수용 원본은 압축하지 않는다.**
- 복사 버튼, 테마 전환, 목차 접기 등 인터페이스 동작은 실제 테스트하고, 실패 시 오류를 표시한다.
- 코드 예제의 `<`, `>`, `&` 등은 HTML 삽입 시 안전하게 이스케이프한다.

## 10. 웹페이지의 코드 박스

1. 모든 실제 소스코드는 **테두리·배경이 있는 독립 코드 박스**에 넣는다.
2. 상단에 **파일명 · 언어 · 예시/원본/검증 상태**를 표시한다.
3. 고정폭 글꼴을 사용하고 **공백·들여쓰기·줄바꿈을 그대로 보존**한다.
4. 긴 코드는 박스 내부에서 가로 스크롤하고, 페이지 전체의 가로 넘침은 방지한다.
5. **코드 복사** 버튼은 실제 소스 텍스트만 복사하며 줄 번호·해설·버튼 라벨을 포함하지 않는다.
6. 줄 번호는 선택 기능이며 복사된 코드에 섞이지 않도록 한다.
7. 큰 화면에서는 코드·해설을 나란히 배치할 수 있지만 좁은 화면에서는 세로로 적층한다.
8. 코드 박스 안에서 글자·주석이 잘리거나 코드 색상이 테마와 충돌하지 않는지 확인한다.
9. 코드 예제에 삽입한 설명이 실제 컴파일·실행을 방해하지 않아야 한다.

## 11. 코드·도식·본문의 정합성

- 코드의 함수명·변수명·신호명·상태명·명령 문자열은 플로우차트·표·설명에 그대로 반영한다.
- 플로우차트의 **처리 단계는 사각형 박스**, **판단은 마름모**, **입출력은 평행사변형**으로 표현한다.
- 판단의 조건은 마름모 안에, ‘예/아니요’는 분기선 옆에 둔다.
- 코드를 줄 단위로 해설할 때는 실제 줄·구문과 해설을 연결한다.
- 개념용 축약 코드와 전체 원본 코드를 명확하게 구분한다.

## 12. 필수 검증 체크리스트

- [ ] 검증된 원본 코드의 기능을 임의로 바꾸지 않았는가?
- [ ] 언어별 들여쓰기와 중괄호·블록 정렬이 일관적인가?
- [ ] 공백과 탭을 혼용하지 않았는가?
- [ ] 함수 인자와 긴 조건식이 읽기 쉽게 줄바꿈되었는가?
- [ ] 주석이 정확한 한글이며 실제 동작과 일치하는가?
- [ ] 변경 표시가 코드 바로 위에 있는가?
- [ ] 삭제된 코드를 실행 소스에 남기지 않았는가?
- [ ] RTL의 순차/조합 동작과 비트 폭을 설명에서 혼동하지 않았는가?
- [ ] 코드 박스가 파일명·언어·복사·스크롤을 지원하는가?
- [ ] 복사된 코드의 공백·줄바꿈이 원본과 동일한가?
- [ ] 코드·도식·본문·테스트 입력이 일치하는가?
- [ ] 코드 수정 후 해당 언어의 구문·컴파일·시뮬레이션 검증을 수행했는가?
- [ ] 수행하지 않은 검증은 ‘미검증’으로 표시했는가?

## 13. 검증 판정

- **통과:** 실제 검사 결과 기준 충족
- **실패:** 검사 결과 문제 확인
- **미검증:** 검사를 수행하지 않음
- **해당 없음:** 해당 파일·언어에 적용되지 않음

**최종 절차:** 원본 확인 → 서식 적용 범위 결정 → 들여쓰기·주석 작성 → 코드 박스 배치 → 코드·도식 정합성 검사 → 실제 구문·실행·렌더링 검증 → 배포.
