# ② 코드 작성·개발 최적화 규칙

**적용 대상:** Verilog/SystemVerilog, C, Python, JavaScript, Shell  
**상태:** 점진적 개선 (② 추가 규칙)  
**핵심:** 코드가 짧아지는 것 자체가 목표가 아닙니다. 정상 동작·설계 품질·재사용성·검증 가능성을 우선합니다.

> **관련 표준:** 코드 들여쓰기·주석·코드 박스는 [`../common/code-style-rules.md`](../common/code-style-rules.md)를 따릅니다.

---

## 1. 코드 재사용

- 새 코드를 작성하기 전에 기존 모듈·함수·라이브러리를 먼저 확인합니다.
- 정상 동작하는 기존 코드는 불필요하게 재작성하지 않습니다.
- 비슷한 기능이 이미 있으면 복제 대신 공통 함수·모듈로 추출합니다.
- 외부 라이브러리 도입 전에 기존 코드로 충분한지 확인합니다.

## 2. 최소 수정

- 오류가 있는 부분만 수정하고, 정상 동작하는 코드는 보존합니다.
- 하나의 작업은 가급적 하나의 목적에 집중합니다.
- 기능 변경과 코드 정리(들여쓰기·주석·리팩터링)는 별도 커밋으로 구분합니다.
- 작은 변경이 연쇄적으로 다른 모듈을 망가뜨리지 않는지 먼저 범위를 파악합니다.

## 3. 불필요한 코드 방지

다음은 작성하지 않습니다:

```
❌ 과도한 추상화 계층 (사용하지 않을 인터페이스·제네릭·팩토리)
❌ 중복 함수 (이미 같은 기능이 있는데 새로 생성)
❌ 사용하지 않는 변수·신호·포트·임포트
❌ 주석 처리된 채로 남겨진 오래된 코드 블록
❌ 설명을 위해 임의로 추가한 `default`·리셋·상태 (RTL)
```

## 4. 코드 품질

- 함수·모듈·변수 이름은 역할을 알 수 있도록 작성합니다.
- RTL에서 포트 방향·폭·클록·리셋 극성은 실제 코드에 맞게 명시합니다.
- 인터페이스 일관성: 같은 프로젝트 내에서 명명 규칙·에러 처리 방식을 통일합니다.
- 코드·도식·본문의 함수명·신호명·상태명은 정확히 일치시킵니다.

## 5. 자동 검증

```
수정 전  → 오류를 먼저 재현하고 원인을 파악합니다.
수정 후  → 해당 언어의 구문·컴파일·시뮬레이션·테스트를 실행합니다.
결과 표기
  - 통과:  실제 실행하여 기준 충족 확인
  - 실패:  실행하여 문제 확인
  - 미검증: 실행하지 않음 (반드시 명시)
```

- 기능 변경이 있으면 가능한 범위에서 테스트벤치·자동 테스트를 먼저 작성합니다.
- 회귀 오류: 수정 후 기존 기능이 망가지지 않았는지 확인합니다.
- 실행하지 않은 검증을 성공했다고 단정하지 않습니다.

## 6. AI 개발 효율

- 간단한 수정을 위해 저장소 전체를 반복해서 읽지 않습니다.
- 관련 파일과 규칙만 선택적으로 읽습니다.
- 불필요한 설계 문서·중간 파일을 생성하지 않습니다.
- 작업을 원자 단위로 쪼깁니다: 큰 변경은 독립적인 작은 단계로 분해합니다.
- 코드를 요청할 때는 코드와 함께 검증 증거(실행 결과·컴파일 로그)도 요청합니다.

## 7. Anti-Pattern (절대 하지 말 것)

```
❌ 작동하는 코드를 "정리"한다며 전체 재작성
❌ 테스트 없이 여러 파일에 걸친 대규모 리팩터링
❌ 오류 원인 파악 전에 임의로 코드 수정
❌ RTL에서 합성 대상 코드와 테스트벤치 코드 혼용
❌ 미검증 코드를 검증 완료로 표기
❌ 원본에 없는 기능을 "개선"이라며 추가
```

## 8. 성능 최적화

- RTL: 타이밍·자원(LUT/FF)·전력은 실제 합성·구현 결과로 판단합니다.
- 소프트웨어: 실행 성능과 메모리 효율은 실제 측정 결과로 판단합니다.
- 최적화는 병목이 확인된 곳에만 적용하고, 추측으로 수정하지 않습니다.

## 9. Ponytail 결정 사다리 (AI 코드 작성 판단 순서)

> 전체 규칙: [`../ponytail/AGENTS.md`](../ponytail/AGENTS.md) 참조  
> Source: https://github.com/DietrichGebert/ponytail (MIT License)

코드를 작성하기 **전에** 아래 순서대로 확인하고, 해당하는 **첫 단계에서 멈춥니다**:

1. 이 기능이 실제로 필요한가? → 아니면 아무것도 하지 않습니다.
2. 코드베이스에 이미 있는가? → 기존 헬퍼·패턴을 재사용합니다.
3. 표준 라이브러리로 해결되는가? → 그것을 씁니다.
4. 네이티브 플랫폼 기능으로 되는가? → 그것을 씁니다.
5. 이미 설치된 의존성으로 되는가? → 그것을 씁니다.
6. 한 줄로 줄일 수 있는가? → 한 줄로 만듭니다.
7. 그래도 필요하다면: 동작하는 최소 코드를 작성합니다.

**사다리 적용 전에 문제를 먼저 이해합니다.** 실제 코드 흐름을 끝까지 읽습니다.

### Ponytail 핵심 규칙

- 요청하지 않은 추상화·보일러플레이트·의존성은 추가하지 않습니다.
- 코드 추가보다 삭제를 우선합니다. 파일 수는 최소로 유지합니다.
- 단순화가 실제 한계를 가진다면 `ponytail:` 주석으로 한계와 개선 방법을 명시합니다.
- 복잡한 요청에는 "정말 X가 필요한가, Y로 충분하지 않은가?"라고 되물어 봅니다.

### Ponytail 적용 예외 (줄이면 안 되는 항목)

- 신뢰 경계의 입력 검증
- 데이터 손실을 막는 오류 처리
- 보안·접근성
- RTL 하드웨어 보정 (클록 드리프트, 센서 오차 등)
- 명시적으로 요청된 모든 기능
